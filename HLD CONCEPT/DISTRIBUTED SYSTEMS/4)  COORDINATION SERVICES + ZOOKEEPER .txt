===============================================================================
0) WHY THIS TOPIC EXISTS IN REAL SYSTEMS
===============================================================================

Before ZooKeeper, first understand the real pain.

In distributed systems, the hardest problem is often NOT storage.
It is COORDINATION.

Storage answers:
“What is the data?”

Coordination answers:
“Who is the leader?”
“Which worker owns this job?”
“Which config version is latest?”
“Who should fail over?”
“Which shard belongs to which node?”
“How do all machines agree on metadata?”

This becomes critical in:
- WhatsApp group server ownership
- Uber driver dispatch leader
- Kafka partition leadership
- HDFS NameNode failover
- Kubernetes control plane metadata
- Payment workflow locks
- Microservice discovery
- Distributed cron scheduling
- Feature flag rollout control

WHY this exists:
Once multiple machines work together, they need a SHARED SOURCE OF TRUTH
for metadata and decisions.

Without coordination:
- split brain
- duplicate processing
- stale configs
- two leaders
- inconsistent failover
- lost distributed locks
- wrong shard routing
- double billing
- duplicate notification sending

This is where coordination services like ZooKeeper exist.

Golden interviewer line:
“Databases store business data, coordination services store system truth.”

1) INTUITION
===============================================================================

Think of ZooKeeper as the “control tower” of distributed systems.

Planes = service nodes
Runways = resources
Tower = ZooKeeper

The tower does NOT fly planes.
It coordinates:
- who lands first
- who waits
- which runway active
- emergency reroute
- failover handling

Same in systems:
ZooKeeper usually does NOT store user data.
It stores CONTROL METADATA.

Examples:
- current leader
- service membership
- locks
- config version
- task ownership
- shard mapping

So intuition:
ZooKeeper = distributed truth manager for cluster coordination.

===============================================================================
2) WHY COORDINATION SERVICE EXISTS
===============================================================================

WHY not just use database table?

Because coordination needs:
- extremely strong consistency
- fast watches / notifications
- ephemeral ownership
- session-based liveness
- ordered updates
- leader election primitives
- tiny metadata reads at huge scale
- fault tolerant quorum

Traditional DB alone is awkward for:
- lock expiry
- leader heartbeat ownership
- membership watches
- failover triggers

Coordination service solves:
“tiny but critical metadata with strong correctness guarantees.”

Real example:
Uber driver dispatch regional leader crash.
Need instant new leader election.
ZooKeeper handles this cleanly.

===============================================================================

Imagine hostel room keys managed by a strict warden.

- only one key per room
- whoever holds key currently owns room
- if student leaves hostel, key auto returns
- others waiting get notified

This is exactly:
- distributed lock

That “auto return on disappearance” is the magic.
This is why ZooKeeper is loved for coordination.

===============================================================================
4) CORE IDEA — WHAT IS ZOOKEEPER
===============================================================================

ZooKeeper is a distributed coordination service.

Its job:
Provide strongly consistent metadata primitives.

Core guarantees:
- linearizable writes
- ordered updates
- watches
- leader election support
- distributed locks
- config management
- membership tracking
- failover metadata
- naming / discovery

Internally it runs as:
LEADER + FOLLOWERS (ensemble)

Usually 3 or 5 nodes.

Write flow:
Client → leader → quorum replicate → commit → ACK

This is conceptually similar to consensus-backed replicated log.

Historically ZooKeeper uses Zab protocol
(ZooKeeper Atomic Broadcast).

===============================================================================
5) WHY ZNODES EXIST
===============================================================================

ZooKeeper stores data as a tree:

/
├── services
│   ├── chat
│   └── payments
├── leaders
├── locks
└── config

These tree nodes = ZNODES

WHY this choice:
Hierarchical metadata is intuitive for system organization.

Problems solved:
- namespace structure
- service grouping
- ownership hierarchy
- lock paths
- config versioning

Tradeoff:
Not suitable for large business datasets.

When NOT to use:
- user profiles
- chat messages
- analytics events
- image metadata at huge scale

ZooKeeper is for CONTROL PLANE metadata, not DATA PLANE scale data.

===============================================================================
6) TYPES OF ZNODES (SUPER IMPORTANT)
===============================================================================

A) PERSISTENT
-----------------------------------
Stays until explicitly deleted.

Use:
- configs
- shard maps
- feature flags

Example:
 /config/payment-service/retry-policy

B) EPHEMERAL
-----------------------------------
Auto deleted when client session dies.

WHY:
Perfect for liveness.

Use:
- service registration
- distributed locks
- leader ownership

Example:
 /leaders/chat-server-1

This solves stale lock problem.

C) SEQUENTIAL
-----------------------------------
Auto numbered.

Example:
 /election/node-00001
 /election/node-00002

Used for:
- fair locks
- leader election ordering
- queues

Interview gold:
“Ephemeral sequential nodes are the most elegant primitive for leader election.”

===============================================================================
7) HOW ZOOKEEPER WORKS (SUPER DETAILED)
===============================================================================

===============================================================================
7.1 READ FLOW
===============================================================================

Reads can come from followers.

WHY:
Read scalability.

Benefit:
High throughput reads.

Tradeoff:
May be slightly stale depending on sync guarantees.

Best for:
- config fetch
- service discovery
- membership list

===============================================================================
7.2 WRITE FLOW
===============================================================================

1. Client sends write to ensemble
2. Routed to leader
3. Leader assigns zxid (ordered transaction id)
4. Followers persist
5. Quorum ACK
6. Commit broadcast
7. Client success

WHY quorum:
Survive machine failure safely.

Consistency:
CP under CAP during partitions.

===============================================================================
7.3 WATCHES
===============================================================================

This is one of the biggest superpowers.

Client can say:
“notify me if this znode changes.”

Example:
 /config/chat-service

When config changes:
all watchers notified.

Used in:
- live config reload
- feature flag rollout
- shard migration
- failover signal
- leader change detection

Netflix / Uber style example:
Dynamic rate limit config updates without restart.

WHY powerful:
Push-based metadata invalidation.

Tradeoff:
Too many watches = memory pressure.

===============================================================================
8) LEADER ELECTION USING ZOOKEEPER
===============================================================================

Classic FAANG follow-up.

FLOW:
1. All nodes create ephemeral sequential znode
2. Smallest sequence wins
3. Others watch predecessor
4. If winner dies, ephemeral node disappears
5. Next smallest becomes leader

Example:
 /election/node-1
 /election/node-2
 /election/node-3

node-1 = leader

If machine crashes:
ZooKeeper removes node-1
node-2 gets watch event
becomes leader

WHY this choice:
Simple, deterministic, strongly consistent.

Tradeoff:
Too frequent elections under flapping network.

===============================================================================
9) DISTRIBUTED LOCKS
===============================================================================

WHY:
Prevent duplicate work.

Examples:
- payment retry processor
- cron scheduler
- inventory reconciliation
- email digest sender
- monthly billing job

Pattern:
Create ephemeral znode:
 /locks/monthly-billing

If success → lock acquired
If exists → retry/watch

Machine crash?
Session expires.
Lock auto released.

Huge benefit:
No stale lock forever.

Tradeoff:
Lock contention bottleneck.

When NOT:
High-throughput hot-key write path.

===============================================================================
10) SERVICE DISCOVERY + MEMBERSHIP
===============================================================================

WHY:
Need real-time active service list.

Each service instance creates ephemeral znode:

 /services/chat/node-1
 /services/chat/node-2

Clients watch /services/chat

If node crashes:
znode auto disappears.

Used in:
- HBase region servers
- Kafka brokers (older versions)
- Dubbo / Java ecosystems
- Hadoop ecosystems

===============================================================================
12) DRAWBACKS / LIMITATIONS
===============================================================================

Jordan’s conclusion section here is very interview-relevant.

A) NOT FOR LARGE DATA
-----------------------------------
Tiny metadata only.

B) LEADER WRITE BOTTLENECK
-----------------------------------
All writes serialized through leader.

C) HOT WATCH PATHS
-----------------------------------
Massive watchers on same node can overload ensemble.

D) SESSION MANAGEMENT COMPLEXITY
-----------------------------------
Timeout tuning tricky.

E) OPERATIONAL OVERHEAD
-----------------------------------
Quorum sizing, disk latency, GC pauses, session flaps.

F) CROSS REGION LATENCY
-----------------------------------
Quorum across regions becomes expensive.

G) HERD EFFECT
-----------------------------------
Too many watchers wake simultaneously.

===============================================================================
13) FAILURE SCENARIOS
===============================================================================

A) MACHINE CRASH
-----------------------------------
Node dies.
If quorum survives, service healthy.

B) LEADER FAILURE
-----------------------------------
Zab elects new leader.

C) NETWORK PARTITION
-----------------------------------
Minority side unavailable.
CP behavior.

D) SESSION TIMEOUT FALSE POSITIVE
-----------------------------------
GC pause/network hiccup may delete ephemeral node.

Can cause:
- lock loss
- false leader failover

Very common production edge case.

E) REGION FAILURE
-----------------------------------
Single region ensemble risky.
Use 3 AZ quorum minimum.

F) SPLIT BRAIN
-----------------------------------
Prevented by quorum + leader protocol.

===============================================================================
14) SCALING BOTTLENECKS
===============================================================================

A) HIGH WRITE CONFIG CHURN
-----------------------------------
ZooKeeper hates frequent write-heavy workloads.

B) LARGE PAYLOADS
-----------------------------------
Keep znode data tiny.

C) TOO MANY CHILDREN
-----------------------------------
Huge child list causes slow watches.

D) MASSIVE WATCHER FANOUT
-----------------------------------
Can create thundering herd.

Solutions:
- shard paths
- hierarchical namespaces
- cache at client side
- watch only parent nodes
- batch config changes

===============================================================================
15) CAP THEOREM + CONSISTENCY TRADEOFF
===============================================================================

ZooKeeper is strongly CP.

During partition:
- prefers consistency
- minority becomes unavailable

WHY:
Wrong leader election is worse than temporary downtime.

Perfect for:
- payments metadata
- shard leadership
- config truth
- failover ownership

Bad for:
- likes counter
- view analytics
- clickstream ingestion
