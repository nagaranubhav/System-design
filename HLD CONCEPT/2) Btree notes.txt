/*
==========================================================================================
🧠 1. INTUITION (ROOT UNDERSTANDING)
==========================================================================================

Think of B-Tree like a "multi-level smart directory system" 📂

Instead of:
    ❌ checking every row (O(N))

We do:
    ✔ Jump in chunks (logarithmic search)

Analogy:
    Phonebook 📖

    - You don’t scan all names
    - You jump: A → M → S → exact name

👉 B-Tree = Sorted + Hierarchical + Balanced

==========================================================================================
🌳 2. WHAT IS A B-TREE?
==========================================================================================

Definition:
    A self-balancing tree where each node contains multiple keys
    and children pointers.

Structure:

            [10 | 20]
           /    |    \
      <10      10-20    >20

✔ Sorted order maintained
✔ Balanced tree (all leaves at same level)

------------------------------------------------------------------------------------------
🧩 Node Structure:
------------------------------------------------------------------------------------------

Each node contains:
    - Keys (sorted)
    - Pointers to children (for navigation)

Example:
    Node = [K1, K2, K3]
    Children = 4 pointers

==========================================================================================
⚙️ 3. HOW B-TREE INDEX WORKS (SEARCH)
==========================================================================================

Goal:
    Find key efficiently

-----------------------------------
🔍 SEARCH FLOW:
-----------------------------------

Step 1:
    Start from ROOT

Step 2:
    Compare key with node keys

Step 3:
    Decide which child to go

Step 4:
    Repeat until leaf node

-----------------------------------
🧠 Example:
-----------------------------------

Tree:
            [10 | 20]
           /    |    \
        [5]   [15]   [25]

Search: 15

    → Compare with [10 | 20]
    → Go to middle child
    → Found 15

✔ Complexity:
    O(log N)

==========================================================================================
⚡ 4. HOW B-TREE READS FROM DISK (VERY IMPORTANT)
==========================================================================================

👉 Each node = Disk Page (block)

Flow:
    1. Load root from disk (or cache)
    2. Traverse node → child pointer
    3. Load next node (disk read)
    4. Repeat

👉 Key insight:
    - Each step = 1 disk I/O
    - Height is small → very few disk reads

🔥 Example:
    1 billion rows → height ~ 3–4

👉 Only 3–4 disk reads → super efficient

==========================================================================================
✍️ 5. HOW B-TREE WRITES (INSERT)
==========================================================================================

-----------------------------------
🧠 INSERT FLOW:
-----------------------------------

Step 1:
    Find correct leaf (search)

Step 2:
    Insert key in sorted order

Step 3:
    If node overflows:
        → Split node

-----------------------------------
🌳 NODE SPLITTING:
-----------------------------------

Example:
    Max keys = 3

    Insert into:
        [10 | 20 | 30]

    After insert 25:
        [10 | 20 | 25 | 30] ❌ overflow

👉 Split:

        [10 | 20]     [25 | 30]
              ↑
        20 moves up to parent

-----------------------------------
⚠️ IMPORTANT:
-----------------------------------

Splitting can propagate up to root

Worst case:
    New root created

==========================================================================================
🗑️ 6. DELETE OPERATION
==========================================================================================

Harder than insert 😬

Cases:
    1. Remove key
    2. If underflow:
        → Borrow from sibling OR
        → Merge nodes

👉 Tree always remains balanced

==========================================================================================
⚡ 7. TIME COMPLEXITY
==========================================================================================

    Search  → O(log N)
    Insert  → O(log N)
    Delete  → O(log N)

👉 Compared to Hash:
    Hash → O(1)
    B-Tree → O(log N)

BUT...

👉 Disk efficiency makes B-Tree faster in real DBs

==========================================================================================
🆚 8. B-TREE vs HASH INDEX (INTERVIEW GOLD)
==========================================================================================

    Feature         | B-Tree           | Hash Index
    ------------------------------------------------
    Search          | O(log N)         | O(1)
    Range Query     | ✅               | ❌
    Sorting         | ✅               | ❌
    Disk Friendly   | ✅🔥             | ❌
    Use Case        | General purpose  | Exact match

👉 Real DBs:
    Use B-Tree as DEFAULT

==========================================================================================
🔥 9. WHY B-TREE IS DISK-FRIENDLY
==========================================================================================

👉 Key reason:

    ✔ High branching factor (many children per node)
    ✔ Shallow tree (small height)
    ✔ Sequential access pattern

👉 Result:
    Fewer disk reads = faster queries

==========================================================================================
🧠 10. WHERE B-TREE INDEX IS STORED
==========================================================================================

👉 Stored on DISK

BUT:

    Frequently accessed nodes → cached in RAM (buffer pool)

Flow:
    Query → Check RAM
        → If miss → load from disk

==========================================================================================
⚠️ 11. WHAT IF SYSTEM CRASHES DURING SEARCH?
==========================================================================================

👉 SEARCH is READ operation

✔ No data modification
✔ No corruption

👉 So:
    Crash during search → SAFE

-----------------------------------
BUT during WRITE:
-----------------------------------

👉 Risk of partial updates

Solution:
    ✔ WAL (Write Ahead Log)

==========================================================================================
🔥 12. WAL IN B-TREE
==========================================================================================

Flow:

    1. Write log
    2. Flush log to disk
    3. Apply change in B-Tree

👉 Ensures:
    Crash recovery

Example:
    If crash during split:
        → WAL replays operation

==========================================================================================
❌ 13. DISADVANTAGES OF B-TREE
==========================================================================================

1. ❌ Slower than hash for exact lookup
2. ❌ More complex (splits, merges)
3. ❌ Write overhead (rebalancing)
4. ❌ More memory for pointers

==========================================================================================
✅ 14. ADVANTAGES OF B-TREE
==========================================================================================

1. ✔ Supports range queries
2. ✔ Supports sorting (ORDER BY)
3. ✔ Disk optimized
4. ✔ Balanced tree (predictable performance)
5. ✔ Used in almost all DBs

==========================================================================================
🧪 15. REAL-WORLD USAGE
==========================================================================================

Queries:

    SELECT * FROM users WHERE id = 10
    SELECT * FROM users WHERE age > 25
    ORDER BY salary

👉 All efficiently handled by B-Tree

Used in:
    - PostgreSQL
    - MySQL (InnoDB default)

==========================================================================================
🚨 16. COMMON INTERVIEW MISTAKES
==========================================================================================

❌ Saying B-Tree is always faster than hash
❌ Ignoring disk I/O factor
❌ Not explaining node splitting
❌ Not mentioning WAL
❌ Confusing B-Tree with Binary Tree

==========================================================================================
🎯 17. INTERVIEW ANSWER TEMPLATE
==========================================================================================

Q: How does B-Tree index work?

Answer:

1. It is a balanced tree storing sorted keys
2. Each node contains multiple keys
3. Search works in O(log N)
4. Very few disk I/Os due to low height
5. Supports range queries and sorting
6. Uses WAL for crash recovery

🔥 Perfect structured answer

==========================================================================================
🧭 18. FINAL MENTAL MODEL
==========================================================================================

B-Tree:

    ✔ Slightly slower than hash (theoretically)
    ✔ MUCH faster on disk (practically)
    ✔ Supports all query types
    ✔ Default choice in databases

👉 Think:
    "Universal index"

==========================================================================================
* END OF MASTER NOTES 🌳🔥
==========================================================================================
*/



/*****************************************************************************************
*        🌳🔥 WHY B-TREE SUPPORTS RANGE QUERIES (DEEP DIVE ADD-ON NOTES) 🔥🌳
*                  (Must-Know Concept • Interview Favorite • Crystal Clear)
*****************************************************************************************/

/*
==========================================================================================
🧠 1. CORE INTUITION (MOST IMPORTANT)
==========================================================================================

👉 B-Tree maintains SORTED ORDER of keys

    Example:
        [5, 10, 15, 20, 25, 30]

👉 Because of sorting:
    ✔ We can traverse sequentially
    ✔ We can get a "range" easily

-----------------------------------
💡 KEY IDEA:
-----------------------------------

    Sorted Data + Linked Traversal = Range Query Possible

==========================================================================================
⚙️ 2. HOW RANGE QUERY WORKS
==========================================================================================

Example Query:
    SELECT * FROM users WHERE age BETWEEN 10 AND 25;

-----------------------------------
🔍 STEP-BY-STEP FLOW:
-----------------------------------

Step 1:
    Find LOWER BOUND (10)
    → Use normal B-Tree search (O(log N))

Step 2:
    Once found:
    → Start scanning forward

Step 3:
    Keep reading next elements until > 25

-----------------------------------
👉 VISUAL:
-----------------------------------

Leaf Nodes (linked):

    [5, 10, 15] → [20, 25, 30] → [35, 40]

Range Query: 10 → 25

    → Start at 10
    → Move right:
        10 → 15 → 20 → 25 ✔
    → Stop at 30 ❌

==========================================================================================
🌳 3. SECRET SAUCE (WHY IT WORKS)
==========================================================================================

👉 Two main reasons:

-----------------------------------
1. SORTED KEYS
-----------------------------------

    Nodes store keys in sorted order

-----------------------------------
2. LEAF NODE LINKING (IMPORTANT 🔥)
-----------------------------------

    Leaf nodes are connected like:

        Node1 → Node2 → Node3

👉 This allows:
    ✔ Sequential scan (like linked list)

==========================================================================================
⚡ 4. TIME COMPLEXITY
==========================================================================================

Range Query:

    O(log N)  → find starting point
    O(K)      → scan K elements

👉 Total:
    O(log N + K)

-----------------------------------
🧠 Compare with Hash:
-----------------------------------

Hash:
    ❌ No ordering
    ❌ No traversal

    → Range Query = O(N) (full scan)

==========================================================================================
❌ 5. WHY HASH INDEX FAILS HERE
==========================================================================================

Hash Example:

    h(10) → bucket 3
    h(15) → bucket 9
    h(20) → bucket 1

👉 No order maintained 😬

👉 So:
    Cannot traverse sequentially

==========================================================================================
🔥 6. REAL DATABASE FLOW
==========================================================================================

Query:
    SELECT * FROM orders WHERE price BETWEEN 100 AND 500;

-----------------------------------
Execution:
-----------------------------------

1. Use B-Tree index on price
2. Jump to first matching value (100)
3. Sequentially scan leaf nodes
4. Stop at 500

👉 Very efficient 🚀

==========================================================================================
🧠 7. EXTRA INSIGHT (INTERVIEW GOLD)
==========================================================================================

👉 B+ Tree (used in real DBs):

    ✔ Data stored ONLY in leaf nodes
    ✔ Leaf nodes are linked

👉 That’s why:
    Range queries are EVEN FASTER

==========================================================================================
🚨 8. COMMON MISTAKE
==========================================================================================

❌ Saying:
    "B-Tree supports range because it's a tree"

✔ Correct answer:
    "Because keys are sorted AND leaf nodes allow sequential traversal"

==========================================================================================
🎯 9. INTERVIEW ANSWER TEMPLATE
==========================================================================================

Q: Why are range queries efficient in B-Tree?

Answer:

1. B-Tree maintains sorted order of keys
2. We first locate the starting point in O(log N)
3. Then we sequentially scan using linked leaf nodes
4. Total complexity becomes O(log N + K)

🔥 Perfect answer

==========================================================================================
🧭 FINAL MENTAL MODEL
==========================================================================================

B-Tree:

    ✔ Sorted structure
    ✔ Linked leaf nodes
    ✔ Efficient sequential traversal

👉 That’s why:
    Range queries = FAST 🚀

==========================================================================================
* END OF RANGE QUERY NOTES 🔥
==========================================================================================
*/
